# AI 기반 잠금화면 To-do List 앱
## 제품 요구사항 정의서 (PRD v1.0)

**문서 상태:** MVP 개발 기준안  
**최초 출시 플랫폼:** iPhone / Apple App Store  
**추후 지원:** Android / Google Play  
**기준일:** 2026년 11월 13일  
**제품명:** 미정 (본 문서에서는 '서비스'로 통칭)  
**레퍼런스:** Took(툭), Shotodo  
**우선순위:** 잠금화면 빠른 입력과 AI 스크린샷 분석 기능에 개발 자원을 집중한다.

# 1. 프로젝트 개요

## 1.1 제품 정의

사용자가 앱을 직접 실행하지 않고도 잠금화면에서 할 일을 빠르게 추가하고, 다른 앱에서 스크린샷을 촬영하면 AI가 이미지 속 할 일을 자동 추출하여 To-do List에 등록할 수 있도록 돕는 모바일 생산성 앱이다.

기존 To-do List 앱의 수동 입력 과정을 최소화하고, 일상에서 발생하는 할 일을 놓치지 않도록 하는 것이 핵심 목적이다.

## 1.2 제품 비전

**"할 일이 생긴 순간 가장 빠르게 기록하고, 휴대폰을 켤 때마다 바로 확인한다."**

서비스의 기본 사용 흐름은 두 가지다.

**A. 직접 입력**

잠금화면 → 추가 버튼 → 텍스트 입력 → 저장 → 목록 반영

**B. AI 자동 추출**

스크린샷 촬영 → AI 분석 → 할 일 추출·요약 → 추가 여부 알림 → 승인 → 목록 반영

두 기능은 동일한 To-do 데이터베이스와 목록 화면을 사용한다.

## 1.3 해결하려는 문제

| 사용자 문제 | 기존 사용 경험 | 제품의 해결 방법 |
|---|---|---|
| 할 일이 생각났지만 기록하기 번거로움 | 잠금 해제 → 앱 찾기 → 실행 → 입력 | 잠금화면에서 바로 입력 |
| 카카오톡·공지에서 할 일이 발생 | 내용을 기억하거나 직접 옮겨 적음 | 스크린샷을 AI가 분석 |
| 긴 문장에서 중요한 내용을 찾기 어려움 | 문장을 읽고 직접 요약 | 실행할 행동과 기한만 추출 |
| 기록한 할 일을 잊어버림 | 별도로 앱을 열어 확인 | 잠금화면에 목록 표시 |
| 캡처한 내용을 나중에 다시 찾아야 함 | 사진첩 검색 | 할 일과 출처 연결 |

**기획 근거**

- Took은 잠금화면 표시와 단축어 입력을 핵심 사용 경험으로 제공한다. [E1]
- Shotodo는 이미지에서 할 일과 일정을 추출해 사용자 확인 후 저장하는 기능을 제공한다. [E2]
- 따라서 두 제품이 해결하는 문제를 하나의 사용 흐름으로 통합하는 것이 제품의 핵심 가설이다.
- 단, 이러한 통합 자체가 시장 수요를 보장하지는 않으므로 초기 사용자 테스트에서 실제 사용 빈도와 유지율을 검증한다.

# 2. 제품 목표 및 성공 기준

## 2.1 주요 목표

1. 잠금화면에서 기기 인증이나 앱 실행 없이 할 일을 추가할 수 있어야 한다.
2. 스크린샷에서 할 일을 AI가 추출하고 이해하기 쉬운 문장으로 요약해야 한다.
3. AI가 분석한 할 일을 사용자가 간단하게 확인하고 저장할 수 있어야 한다.
4. 저장한 할 일은 앱과 잠금화면 목록에 반영되어야 한다.
5. 한국어 문장과 날짜 표현을 우선 지원해야 한다.
6. Android와 향후 일정 공유 기능을 위해 확장 가능한 데이터 구조를 사용해야 한다.

## 2.2 핵심 성공 지표

아래 수치는 실제 성능 측정값이 아닌 **MVP 개발 및 베타 테스트의 목표치**다.

| 지표 | 초기 목표 | 측정 방법 |
|---|---|---|
| 잠금화면 빠른 추가 성공률 | 99% 이상 | 잠금 상태 입력 테스트 |
| 잠금화면 입력 소요 시간 | 중앙값 5초 이내 | 버튼 탭~저장 완료 |
| AI 분석 후 알림까지 | 정상 네트워크 기준 P90 15초 이내 | 저장 시각~알림 시각 |
| 실제 할 일 식별 정밀도 | 90% 이상 | 평가 데이터 정답 비교 |
| 명시된 마감일 추출 정확도 | 95% 이상 | 한국어 날짜 평가 |
| AI 분석 결과 저장 성공률 | 99% 이상 | 추가 버튼 처리 로그 |
| 동일 캡처 중복 등록률 | 1% 미만 | 중복 분석 테스트 |
| 앱 강제 종료 후 데이터 보존 | 100% | 재실행 및 재부팅 테스트 |

iOS의 백그라운드 실행과 위젯 갱신에는 운영체제 제한이 존재하므로 지연 시간 목표를 모든 상황에서 보장한다고 홍보하지 않는다.

# 3. 타깃 사용자

## 3.1 주요 사용자

**대학생**

- 카카오톡 팀 프로젝트 대화
- 과제 공지 및 LMS 화면
- 시험 일정
- 발표 준비와 제출 기한

**직장인**

- 업무 메신저 대화
- 회의 후속 작업
- 이메일 요청
- 제출 및 검토 일정

**일반 사용자**

- 예약 확인
- 결제·배송 관련 할 일
- 개인적인 약속
- 일상적인 할 일

## 3.2 주요 사용 시나리오

**시나리오 A: 빠른 입력**

사용자가 이동 중 '집에 가서 택배 보내기'가 생각난다.

휴대폰의 잠금화면을 켜고 추가 버튼을 누른 뒤 해당 내용을 입력한다. 앱을 직접 실행하지 않아도 할 일이 저장된다.

**시나리오 B: AI 캡처**

카카오톡에서 다음 메시지를 받는다.

"다음 주 화요일 오후 5시까지 발표자료 수정해서 보내줘."

사용자는 대화 화면을 캡처한다.

AI는 다음 정보를 추출한다.

- 할 일: 발표자료 수정 후 전달
- 마감일: 다음 주 화요일 17:00
- 상태: 확인 대기

사용자는 알림에서 '추가'를 누른다.

**시나리오 C: 일정이 여러 개인 공지**

한 장의 이미지에 과제 제출, 팀 회의, 발표 일정이 포함되어 있다.

AI는 세 개의 항목을 추출한다. 사용자에게 '할 일 3개를 발견했어요'라고 알리고, 사용자는 검토 화면에서 원하는 항목만 등록한다.

**기획 근거:** 하나의 캡처에 여러 작업이 있을 수 있으므로 이미지 하나를 무조건 작업 하나로 변환하지 않는다. Shotodo 역시 다중 항목 추출과 저장 전 검토를 지원한다. [E2]

# 5. 핵심 기능 ① 잠금화면 To-do List

## 5.1 기능 목표

사용자가 기기를 잠금 해제하거나 앱을 실행하지 않고 새로운 할 일을 간단하게 입력하고 저장할 수 있어야 한다.

**레퍼런스:** Took(툭)

## 5.2 핵심 사용자 흐름

1. 사용자가 아이폰의 잠금화면을 켠다.
2. 잠금화면의 '할 일 추가' 버튼을 누른다.
3. iOS의 텍스트 입력 대화상자가 표시된다.
4. 사용자가 할 일을 입력한다.
5. 완료 버튼을 누른다.
6. 시스템이 내용을 저장한다.
7. 잠금화면 목록 갱신을 요청한다.
8. 사용자는 앱을 실행하지 않고 입력을 마친다.

목표는 버튼을 눌렀을 때 앱의 메인 화면으로 이동하지 않는 것이다.

## 5.3 구현 방법

**기본 방식**

- Apple Shortcuts
- `Ask for Input`
- App Intents
- `authenticationPolicy = .alwaysAllowed`
- 공유 로컬 데이터 저장소

예상 구조:

잠금화면 추가 버튼 → 단축어 입력 요청 → AddTodo App Intent → 로컬 저장 → 잠금화면 갱신 요청

단축어 입력 요청은 텍스트를 받으며 App Intent는 전달받은 텍스트를 저장한다.

**중요한 구현 조건**

App Intent가 잠긴 상태에서도 실행 가능하다는 사실만으로 iOS의 모든 입력 UI가 인증 없이 동작한다고 보장되지는 않는다.

따라서 다음 항목을 출시 차단 조건으로 설정한다.

- Face ID 인증 없이 입력 대화상자를 열 수 있는가?
- 앱 메인 화면으로 전환되지 않는가?
- 입력 후 저장이 정상적으로 실행되는가?
- 저장에 필요한 로컬 데이터가 잠금 상태에서 접근 가능한가?

실기기 테스트에서 모두 통과해야 P0 기능을 완료로 판정한다.

**기술 근거:** Apple App Intents의 `alwaysAllowed` 인증 정책, Shortcuts의 `Ask for Input`. [E3][E4]

## 5.4 잠금화면 표시 방식

두 가지 UI를 병행한다.

### A. 작은 잠금화면 위젯

`WidgetKit` 사용.

표시 내용:

- 다음 할 일 1개 또는 2개
- 남은 할 일 수
- 가장 가까운 마감일

시계 아래의 제한된 공간에 맞추어 간략하게 표시한다.

### B. 큰 잠금화면 목록 카드

`ActivityKit`의 Live Activity 사용.

표시 내용:

- 오늘의 할 일
- 진행되지 않은 작업
- 완료 상태
- 남은 개수

**MVP 기본 디자인 목표**

- 기본적으로 3~5개의 할 일 표시
- 글자가 길면 한 줄 또는 두 줄로 축약
- 새로운 할 일은 사용자가 설정한 순서에 따라 배치
- 완료 항목은 아래로 이동하거나 숨김 처리
- 목록이 비어 있을 때 안내 문구 표시

단, 실제 화면 높이와 표시 가능한 개수는 기기 및 iOS 버전에 따라 달라질 수 있다.

## 5.5 Live Activity 생명주기

Apple 공식 정책상 일반적인 Live Activity는 최대 8시간 활성 상태를 유지하고, 이후 잠금화면에 최대 4시간 추가로 표시될 수 있다. [E5]

따라서 다음을 설계한다.

- 사용자가 잠금화면 목록을 활성화할 수 있는 설정
- 앱 실행 시 목록 카드 상태 확인
- 카드 종료 시 복구 경로 제공
- 시스템이 허용하는 범위에서 재시작 및 갱신
- 상시 표시가 실패했을 때 작은 WidgetKit 위젯으로 주요 정보 제공

**Took 레퍼런스:** 툭은 자동 재시작을 통해 하루 종일 카드를 유지한다고 안내한다. 같은 사용자 경험을 목표로 하되, 시스템이 언제나 백그라운드 재시작을 허용한다고 가정하지 않는다. [E1][E5]

## 5.6 할 일 표시 규칙

기본 정렬 순서:

1. 오늘 마감인 미완료 항목
2. 마감이 지난 미완료 항목
3. 마감이 지정되지 않은 항목
4. 완료 항목

기본 정렬 외에 수동 정렬을 추후 제공한다.

사용자가 선택하지 않은 우선순위를 AI가 임의로 확정하지 않는다.

## 5.7 할 일 추가 규칙

- 텍스트가 비어 있으면 저장하지 않는다.
- 앞뒤 공백은 제거한다.
- 입력 내용이 너무 길면 제한을 안내한다.
- 저장 전에 불필요한 확인 팝업을 띄우지 않는다.
- 저장 성공 시 간단한 시스템 피드백을 제공한다.
- 같은 내용의 수동 입력은 원칙적으로 허용한다.
- 네트워크 연결 없이 저장 가능해야 한다.

## 5.8 잠금화면 완료 처리

완료 버튼은 가능한 범위에서 제공한다.

하지만 Apple 공식 문서에 따르면 일반 WidgetKit 및 Live Activity의 잠금화면 버튼과 토글은 기기가 잠겨 있으면 인증과 잠금 해제를 요구할 수 있다. [E6]

따라서 **인증 없는 빠른 추가는 P0 필수**, **잠긴 상태에서 인증 없는 완료 토글은 별도 기술 검증 대상**으로 구분한다.

완료 토글이 제한될 경우에도 빠른 입력 기능은 영향을 받지 않도록 구현한다.

## 5.9 사용자 수용 기준

- 잠금화면에서 입력 시작
- 입력 취소 시 저장되지 않음
- 입력 완료 시 정확히 한 번 저장
- 저장 후 앱 내 목록과 데이터 일치
- 네트워크가 없어도 빠른 추가 가능
- 잠금 상태에서 불필요한 인증 화면 없음
- OS 제한으로 목록 갱신이 지연되더라도 데이터 손실 없음

# 6. 핵심 기능 ② 스크린샷 AI 자동 To-do 생성

## 6.1 기능 목표

사용자가 다른 앱에서 스크린샷을 저장했을 때 AI가 이미지의 텍스트를 분석하고 할 일을 발견하면 추가 여부를 묻는다.

**레퍼런스:** Shotodo

## 6.2 지원하는 이미지

1차 지원 대상:

- 카카오톡 대화
- 문자 메시지
- 이메일
- 학교 및 회사 공지
- 일정표
- 웹페이지
- 일반 이미지 안의 텍스트

이미지를 무조건 할 일로 변환하지 않는다.

다음 이미지는 기본적으로 제외한다.

- 할 일이 없는 풍경 사진
- 일반적인 SNS 게시물
- 단순한 제품 이미지
- 날짜나 업무와 관련 없는 사진
- 작업 지시가 없는 대화

사용자가 명시적으로 할 일 생성을 요청한 경우에는 별도로 분석을 시도할 수 있다.

## 6.3 자동 실행 구조

iOS 27 이상에서 사용자가 단축어 자동화를 설정한 경우 다음 순서로 동작한다.

1. 사용자가 다른 앱에서 스크린샷을 촬영한다.
2. 스크린샷이 지정된 위치에 저장된다.
3. iOS의 스크린샷 자동화가 실행된다.
4. 단축어가 분석 대상 이미지를 확보한다.
5. 서비스의 App Intent에 이미지를 전달한다.
6. OCR을 실행한다.
7. AI가 텍스트에서 실제 할 일을 추출한다.
8. 추출된 할 일이 있으면 추가 제안 알림을 생성한다.
9. 사용자가 승인하면 To-do DB에 저장한다.

**기술 근거:** iOS 27 단축어의 스크린샷 자동화. [E7]

### 중요한 기술 검증 항목

스크린샷 자동화 트리거가 있다는 사실과 해당 스크린샷 이미지가 App Intent로 항상 정확하게 전달된다는 것은 다른 문제다.

개발 초기에 다음을 검증한다.

- 스크린샷 자동화 입력으로 이미지가 직접 전달되는지
- 전달되지 않는 경우 최근 스크린샷을 안전하게 가져올 수 있는지
- 저장 위치가 사진·파일·클립보드일 때 동작이 달라지는지
- 스크린샷을 연속 촬영했을 때 이미지가 섞이지 않는지
- 앱이 종료된 상태에서도 분석 동작이 실행되는지
- 단축어의 개인정보 접근 허용을 처음 한 번만 받도록 설정할 수 있는지

최근 사진 가져오기 방식을 사용할 경우 다른 사진을 잘못 분석하는 위험이 있으므로 생성 시간, 파일 종류, 중복 식별값 등을 확인한다.

## 6.4 사용자 초기 설정

앱 설치만으로 모든 스크린샷 자동화를 켤 수 있다고 가정하지 않는다.

온보딩에서 사용자가 직접 설정하도록 안내한다.

**설정 단계**

1. 앱 최초 실행
2. 핵심 기능 설명
3. 알림 권한 요청
4. AI 분석 개인정보 처리 동의
5. '스크린샷 자동 추가 설정' 선택
6. 단축어 자동화 연결 안내
7. 테스트 캡처 실행
8. 분석 결과 또는 테스트 성공 상태 확인

설정 성공 여부를 실제 테스트 결과로 판단하며, 사용자가 단축어 화면을 방문한 것만으로 성공 처리하지 않는다.

## 6.5 AI 처리 파이프라인

**단계 1 — 이미지 수신**

- 이미지 식별값 생성
- 처리 시간 기록
- 중복 이미지 여부 확인
- 파일 형식과 크기 확인
- 잘못된 입력 차단

**단계 2 — OCR**

이미지에서 텍스트와 위치 정보를 추출한다.

iOS에서는 Apple Vision을 우선 사용한다.

OCR 처리 자체는 가능한 한 기기 내에서 수행한다.

**단계 3 — 전처리**

- 불필요한 공백 제거
- 대화 순서 복원
- 날짜·시간 표현 정규화
- 중복 문장 제거
- 텍스트가 없는 이미지 판별

**단계 4 — AI 의미 분석**

AI가 다음을 판단한다.

- 사용자가 해야 하는 행동이 있는가?
- 그 행동은 무엇인가?
- 누가 수행해야 하는가?
- 언제까지 해야 하는가?
- 다른 할 일과 분리해야 하는가?
- 원문이 명령인지, 단순 설명인지?
- 추론 근거가 충분한가?

**단계 5 — 결과 검증**

- OCR 근거와 AI 추출 문장 대조
- 날짜 해석 검증
- 존재하지 않는 정보 생성 여부 확인
- 중복 할 일 검사
- 사용자 확인이 필요한 항목 분류

**단계 6 — 추가 제안**

실제 할 일이 있으면 알림을 발송한다.

없으면 기본적으로 아무 알림도 보내지 않는다.

## 6.6 AI 결과 데이터 형식

AI는 단순한 자연어 문장이 아닌 구조화된 데이터를 반환해야 한다.

| 필드 | 의미 |
|---|---|
| `is_actionable` | 실제 할 일 여부 |
| `title` | 요약된 할 일 제목 |
| `description` | 필요한 추가 설명 |
| `due_at` | 확정 가능한 마감일시 |
| `due_precision` | 날짜만 확정 / 시각까지 확정 |
| `assignee` | 수행 주체 |
| `confidence` | 분석 신뢰도 |
| `evidence_text` | 원본에서 판단 근거가 된 문장 |
| `needs_confirmation` | 추가 검토 필요 여부 |
| `suggested_category` | 선택적 분류 |
| `source_type` | 이미지 또는 사용자 직접 입력 |

배열로 여러 할 일을 반환할 수 있어야 한다.

필요하면 하나의 이미지에서 0개, 1개 또는 여러 개의 할 일이 추출될 수 있다.

## 6.7 AI 요약 규칙

**원칙 1. 짧고 행동 중심으로 작성한다.**

원문:

"우리 다음 주 금요일까지 자료 최종 정리해서 교수님한테 보내야 할 것 같아."

결과:

"발표자료 최종 정리 및 교수님께 전달"

**원칙 2. 명시되지 않은 날짜는 만들어내지 않는다.**

원문:

"나중에 보고서 한번 확인해 줘."

결과:

- 제목: 보고서 확인하기
- 마감일: 미지정

**원칙 3. 상대방의 할 일을 내 할 일로 잘못 판단하지 않는다.**

원문:

"나는 포스터 만들게. 너는 발표자료 준비해 줘."

결과:

"발표자료 준비하기"

단, 대화 상대 중 누가 실제 앱 사용자인지 확정할 수 없다면 자동으로 단정하지 않고 확인을 요청한다.

**원칙 4. 날짜는 캡처 시점과 실제 문맥을 기준으로 해석한다.**

'내일' 같은 상대적 날짜는 메시지가 작성된 날짜와 캡처 날짜가 다를 수 있으므로 주의한다.

**원칙 5. AI가 실제 작업을 수행했다고 주장하지 않는다.**

할 일을 생성했다는 것과 할 일을 완료했다는 것은 구분한다.

## 6.8 신뢰도에 따른 처리 정책

초기 임계값은 추후 평가 데이터로 보정한다.

| 분석 결과 | 처리 |
|---|---|
| 명확한 할 일 | 추가 제안 |
| 여러 할 일 | 일괄 검토 알림 |
| 수행 주체가 불명확 | 확인 필요 표시 |
| 마감일만 불명확 | 제목은 제안, 날짜는 미지정 |
| 할 일이 없음 | 알림 발송 안 함 |
| OCR 실패 | 수동 재시도 안내 |
| AI 분석 실패 | 재시도 대기 상태 저장 |

AI의 confidence 값은 실제 정확도를 보장하는 확률로 간주하지 않는다. 별도의 평가 데이터로 임계값을 교정한다.

# 7. AI 분석 결과 알림

## 7.1 알림 설계 원칙

알림은 사용자에게 추가 행동을 강요하지 않고, 발견된 할 일을 간단하게 승인할 수 있도록 한다.

`UserNotifications`의 액션형 알림을 사용한다. [E8]

## 7.2 할 일 한 개를 찾았을 때

**알림 제목**

새로운 할 일을 발견했어요

**내용**

발표자료 수정 및 전달  
마감: 11월 20일 오후 5시

**버튼**

- 추가
- 무시

'추가'를 누르면 앱을 전면 실행하지 않고 저장하는 백그라운드 액션을 우선 구현한다.

앱이 잠긴 상태에서의 동작은 실제 기기에서 검증한다.

## 7.3 할 일이 여러 개일 때

**알림 제목**

할 일 3개를 발견했어요

**내용**

캡처한 공지에서 제출 일정과 준비할 작업을 추출했어요.

**버튼**

- 확인하기
- 무시

'확인하기'를 누르면 검토 화면으로 이동한다.

검토 화면 기능:

- 추출 항목 체크
- 제목 수정
- 날짜 수정
- 전체 선택
- 선택 항목 저장

여러 항목을 확인 없이 일괄 저장하는 것은 기본 동작으로 사용하지 않는다.

## 7.4 알림 정책

- 할 일이 없는 이미지에 알림을 보내지 않는다.
- 동일한 캡처의 동일한 결과를 반복 알리지 않는다.
- 사용자에게 무시한 항목을 다시 강제로 제안하지 않는다.
- 사용자가 알림을 비활성화하면 앱 내 분석함에 결과를 남긴다.
- 기기 알림 집중 모드 및 OS 알림 정책을 존중한다.
- 잠금화면의 알림에는 민감한 원문을 그대로 표시하지 않는다.
- 처리 완료 전 잠정 결과를 확정된 할 일처럼 표시하지 않는다.

## 7.5 알림 수용 기준

- 승인 버튼 한 번으로 정확히 한 번 등록
- 무시 버튼 시 등록되지 않음
- 알림을 늦게 열어도 처리 가능
- 다른 곳에서 이미 등록한 항목이면 중복 생성하지 않음
- 네트워크 오류 시 데이터 손실 없음
- 등록 후 잠금화면 갱신 요청

# 8. 앱 화면 및 UI 설계

## 8.1 디자인 철학

**Minimal, Fast, Readable**

- 필수 정보를 우선 표시
- 한 번의 행동으로 하나의 작업 완료
- 불필요한 애니메이션 최소화
- 텍스트 가독성 우선
- 잠금화면과 앱 화면의 디자인 일관성 유지

툭의 간결한 사용성을 참고하되 해당 제품의 UI를 그대로 복제하지 않는다.

## 8.2 필수 화면

### 화면 1. 홈 / 오늘의 할 일

구성 요소:

- 오늘 날짜
- 남은 할 일 수
- 미완료 To-do 목록
- 완료 To-do 목록
- 할 일 추가 입력창
- 캡처 분석함 접근
- 설정 메뉴

할 일 항목 표시:

- 체크박스
- 제목
- 선택적 마감일
- AI 생성 여부 표시
- 상세보기

### 화면 2. 할 일 상세

구성 요소:

- 제목 편집
- 설명
- 마감 날짜·시간
- 완료 상태
- 생성 출처
- 삭제
- 저장

AI 생성 항목은 필요하면 원문 근거를 확인할 수 있게 한다. 원본 이미지 보존 여부는 개인정보 설정을 따른다.

### 화면 3. AI 분석 검토

구성 요소:

- 분석된 이미지 미리보기
- 추출된 할 일 목록
- 각 항목 선택 체크박스
- 제목과 날짜 편집
- 선택 항목 저장
- 모두 무시
- 분석 오류 신고

### 화면 4. AI 분석함

상태 구분:

- 확인 대기
- 저장 완료
- 무시
- 분석 실패

분석 결과와 실제 등록된 할 일이 구분되도록 설계한다.

### 화면 5. 설정

구성 요소:

- 잠금화면 목록 사용 설정
- 잠금화면 빠른 추가 설정
- 캡처 자동화 설정
- 자동화 테스트
- 알림 권한 상태
- AI 분석 동의 및 처리 정책
- 잠금화면 개인정보 표시 설정
- 데이터 내보내기 및 삭제
- 앱 버전
- 고객지원 및 개인정보 처리방침

## 8.3 온보딩

최초 실행 시 사용자에게 두 핵심 가치를 설명한다.

**1단계:** 잠금화면에서 바로 할 일 추가

**2단계:** 캡처만으로 AI가 할 일 제안

**3단계:** 필요한 권한 및 단축어 설정

**4단계:** 샘플 할 일 입력·캡처 분석 테스트

각 권한은 해당 기능을 사용하기 직전에 요청한다.

사용자가 AI 기능을 원하지 않으면 수동 To-do List로 계속 사용할 수 있어야 한다.

# 9. 기술 아키텍처

## 9.1 권장 기술 스택

**앱 프레임워크**

React Native + Expo + TypeScript

선택 이유:

- iOS와 Android에서 상당 부분의 화면과 비즈니스 로직 공유
- Windows 노트북에서 프론트엔드 개발 가능
- Fast Refresh로 실제 아이폰 화면을 보면서 수정 가능
- Expo EAS 클라우드 빌드로 iOS 빌드 및 배포 가능
- 향후 Android 구현 시 UI 재사용 가능

**iOS 전용 코드**

Swift + SwiftUI

필요한 구성:

- WidgetKit Extension
- ActivityKit
- App Intents
- Shortcuts 연결
- Apple Vision OCR
- Share Extension
- UserNotifications
- App Groups

이 영역은 React Native만으로 해결하지 않고 네이티브 모듈 또는 iOS 확장으로 개발한다.

Expo Go만으로 모든 기능을 테스트할 수 없으므로 실제 Development Build를 사용한다.

**근거:** Expo는 클라우드 빌드와 네이티브 앱 확장을 지원하지만 앱 확장은 별도 네이티브 설정이 필요하다. [E9][E10]

## 9.3 저장소

MVP는 **로컬 우선(Local-first)** 구조를 권장한다.

기본 작업 데이터는 기기에 저장한다.

- 일반 앱 UI
- 단축어 App Intent
- 위젯 Extension

세 영역이 동일한 작업 상태를 사용할 수 있도록 App Groups 기반 공유 저장소를 사용한다.

저장 기술은 SQLite를 우선 검토한다.

SQLite 접근은 공통 저장소 계층을 통해 수행하고, 앱과 Extension이 동시에 데이터를 변경하는 상황에 대비한다.

잠금 상태에서 접근 가능한 데이터 보호 정책도 별도로 설계해야 한다. 인증 없는 빠른 저장과 개인정보 보호 사이의 균형이 필요하다.

## 9.4 AI 아키텍처

**OCR**

- Apple Vision 우선
- 한국어·영어 테스트
- 이미지를 서버에 보내지 않는 구조 우선

**LLM**

- 한국어 문맥 이해
- 구조화된 결과 반환
- 날짜 정규화
- 수행 주체 판단
- 다중 작업 추출

MVP에서는 특정 AI 모델을 제품 구조에 강하게 결합하지 않는다.

`TaskExtractionProvider`와 같은 추상화 계층을 만들어 모델 교체를 가능하게 한다.

**권장 초기 방식**

1. 온디바이스 OCR
2. 추출 텍스트 정제
3. 한국어 성능 검증을 통과한 LLM에 전달
4. 구조화된 결과 검증
5. 사용자 승인 후 저장

온디바이스 모델을 지원하는 기기에는 향후 로컬 분석 옵션을 제공할 수 있다.

Apple Foundation Models 사용 시 기기 지원과 실제 한국어 성능을 검증해야 한다. [E11]

## 9.5 클라우드 백엔드

첫 버전은 계정 없이 사용할 수 있도록 한다.

다만 외부 AI API가 필요한 경우 최소한의 서버 계층을 둘 수 있다.

서버 역할:

- AI API 키 보호
- 호출량 제한
- 모델 요청 전달
- 응답 형식 검사
- 장애 및 비용 모니터링

앱 바이너리에 공용 AI API 비밀키를 넣지 않는다.

사용자 계정과 친구 일정 공유를 위한 서버 기능은 후속 버전에서 본격적으로 개발한다.

# 11. 개인정보 보호 및 보안

## 11.1 설계 원칙

**사용자가 촬영한 모든 스크린샷에는 개인정보가 포함될 가능성이 있다.**

따라서 기능 편의성보다 사용자 동의와 데이터 최소화를 우선한다.

## 11.2 처리 규칙

- 스크린샷 분석은 사용자가 기능을 명시적으로 활성화한 경우에만 실행한다.
- OCR은 가능한 한 기기 내에서 처리한다.
- 외부 AI에 전송하는 데이터 범위를 명확하게 고지한다.
- 외부 AI로 전송하기 전에 사용자 동의를 받는다.
- 계좌번호, 비밀번호, 인증코드 등 민감한 문자열을 감지하면 분석을 제한하거나 제외한다.
- 민감정보 자동 제거의 정확도를 보장할 수 없으므로 제거만을 유일한 보호 수단으로 사용하지 않는다.
- 서버에 원본 이미지를 기본적으로 저장하지 않는다.
- 저장하지 않은 분석 원문은 처리 완료 또는 보존 기한에 따라 삭제한다.
- 사용자가 AI 기능을 끌 수 있도록 한다.
- 사용자에게 데이터 삭제 방법을 제공한다.

**근거:** Apple App Store Review Guidelines 5.1.1, 5.1.2. [E12]

## 11.3 잠금화면 개인정보 노출

잠금화면은 다른 사람이 볼 수 있으므로 별도 표시 설정을 둔다.

**표시 옵션**

- 할 일 제목 표시
- 할 일 개수만 표시
- 잠금화면 내용 숨김

기본값은 핵심 기능 사용성을 유지하되, 온보딩에서 노출 위험을 설명하고 선택할 수 있도록 한다.

AI가 추출한 개인 대화 원문을 잠금화면에 그대로 표시하지 않는다.

## 11.4 데이터 보존 정책

초기 제안:

- 등록된 할 일: 사용자가 삭제할 때까지 유지

위 보존 기간은 제품 정책 초안이며 출시 전에 개인정보 처리방침과 일치시켜야 한다.

# 12. 오류 및 예외 처리

## 12.1 스크린샷 자동화가 설정되지 않은 경우

사용자가 직접 사진을 선택하거나 공유 메뉴에서 분석할 수 있도록 한다.

## 12.2 알림 권한이 없는 경우

분석 자체를 중단할 필요는 없다.

분석 결과는 앱의 '확인 대기' 목록에 저장하고 알림 권한을 설정에서 변경할 수 있게 한다.

## 12.3 네트워크가 없는 경우

- 잠금화면 수동 입력은 정상 저장
- OCR이 기기 내에서 가능하면 계속 진행
- 클라우드 AI 분석은 재시도 대기
- 분석하지 못한 항목을 성공으로 표시하지 않음

## 12.4 AI가 잘못 추출한 경우

- 제목과 날짜 수정 가능
- 원문 근거 확인 가능
- 결과 무시 가능
- 같은 이미지 재분석 가능
- 사용자 수정 사항은 해당 항목에 저장

## 12.5 중복 캡처

이미지 지문과 시간·텍스트 유사도를 사용해 중복을 판별한다.

중복 의심 시 기존 항목을 보여주되, 실제로 서로 다른 작업을 잘못 합치지 않도록 한다.

## 12.6 잠금화면 목록이 갱신되지 않은 경우

실제 DB 저장 성공 여부를 우선 확인한다.

- 저장 성공 상태 유지
- 위젯 타임라인 갱신 요청
- 필요하면 Live Activity 상태 갱신
- 앱 진입 시 최신 데이터 재동기화

위젯 화면 갱신 실패가 작업 데이터 손실로 이어져서는 안 된다.

- 자동 스크린샷 분석: iOS 27 이상에서 우선 지원
- 자동화가 지원되지 않는 버전: 공유 메뉴·사진 선택 분석 제공

이렇게 하면 오래된 iPhone 사용자도 기본 To-do 기능을 사용할 수 있다.

다만 자동 스크린샷 기능을 핵심으로 홍보할 때는 지원 iOS 버전을 명확하게 표시한다.

기능별 최소 OS 지원 범위는 사용한 네이티브 API의 실제 배포 타깃을 기준으로 확정한다.

## 15.2 Android 확장 설계

React Native 화면과 공통 비즈니스 로직을 재사용한다.

Android 전용으로 개발해야 할 영역:

- 알림
- 잠금화면 빠른 접근
- 스크린샷 입력 경로
- OCR 연동
- 위젯·퀵세팅
- 백그라운드 작업 처리

**중요:** iOS의 스크린샷 자동화 동작을 Android에서 그대로 재현할 수 있다고 가정하지 않는다.

Android 14의 공식 스크린샷 감지 API는 기본적으로 해당 앱의 화면이 보이는 동안의 스크린샷을 감지하며, 스크린샷 이미지 자체를 전달하지 않는다. [E13]

따라서 Android 첫 버전은 다음 방식으로 설계한다.

- 이미지 공유 → AI 분석
- 갤러리에서 이미지 선택
- Android에서 허용하는 빠른 실행 기능
- 기기별 잠금화면 지원 범위에 맞는 알림·바로가기

Android의 자동 캡처 감지는 OS 권한 및 배포 정책을 확인한 뒤 별도 연구 과제로 진행한다.

# 20. 출시 전 반드시 결정할 사항

**D-01. 잠금화면 입력 방식**

1순위는 Took과 유사한 단축어 기반 텍스트 입력이다.

실기기에서 인증 없는 입력이 실패하면 시스템이 지원하는 다른 입력 경로를 검토한다. 필수 경험을 충족하지 못하면 그대로 출시하지 않는다.

**D-02. 잠금화면 목록 방식**

작은 WidgetKit 위젯은 기본 제공한다.

큰 목록은 Live Activity를 우선 구현하되, 만료와 갱신 제약을 고려해 기능 안정성을 검증한다.

**D-03. AI 모델**

한국어 평가 데이터로 실제 정확도를 측정한 뒤 선택한다.

추론 비용과 속도 외에 수행 주체 판단, 날짜 정확도, 불필요한 할 일 생성률을 함께 비교한다.

**D-04. 스크린샷 자동화**

iOS 27 자동화 경로를 우선 검증한다.

자동화 설정이 실패하더라도 서비스가 동작하도록 수동 경로를 유지한다.

**D-05. 개인정보 처리**

기기 내 OCR을 기본으로 하고 외부 AI 사용 시 명확한 동의를 받는다.

**D-06. 계정 정책**

MVP는 로그인 없이 사용하고, 미래 공유 기능을 위해 계정 및 동기화가 추가 가능한 구조로 설계한다.

# 23. 최종 제품 원칙

이 제품은 기능이 많은 일정 관리 앱을 목표로 하지 않는다.

사용자가 가장 자주 하는 두 가지 행동, 즉 **생각난 할 일을 즉시 적는 것**과 **다른 곳에서 발견한 할 일을 기록하는 것**에 집중한다.

따라서 초기 제품의 경쟁력은 다음 세 가지로 판단한다.

**첫째, 빠른 입력.** 잠금화면에서 별도 인증 없이 기록할 수 있어야 한다.

**둘째, 정확한 AI 분석.** 스크린샷에서 실제로 해야 할 일만 찾아내고, 사용자가 이해하기 쉬운 한 문장으로 정리해야 한다.

**셋째, 최소한의 조작.** AI가 제안한 내용을 사용자가 한 번의 확인으로 저장하고, 필요할 때 잠금화면에서 볼 수 있어야 한다.
